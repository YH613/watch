# watch

URL の変化を見張って Discord に知らせる。GitHub Actions で動く。
**`schedule` だけでは 10 分ごとに回らない**（下記「実行間隔」）。

対応しているのは 2 種類。

| adapter | 内容 |
|---|---|
| `static_html` | ページ本文のハッシュ比較（script / style は無視） |
| `playwright_grow` | JS で描画される予約枠の空き状況 |

## 使い方

リポジトリの Settings → Secrets and variables → Actions に 2 つ登録する。

| Secret | 中身 |
|---|---|
| `DISCORD_WEBHOOK_URL` | Discord のウェブフック URL |
| `WATCH_CONFIG` | 監視対象の YAML（下記） |

監視対象をリポジトリに置かないので、公開しても何を見ているかは分からない。

```yaml
collections:
  - name: pages
    mode: watch
    adapter: static_html
    schedule:
      skip_hours_jst: [7]        # この時間帯は動かさない
    notify:
      templates:
        changed: "[{label}] 更新があります"
        first_detect: "[{label}] 更新があります"
    sources:
      - url: https://example.com/a.html
        label: A                  # 通知に出る名前。省略可
```

`{label}` と `{url}` がテンプレートで使える。URL は通知本文ではなく
埋め込みに入る（スマホのプッシュ通知が URL で埋まらないように）。

## 手元で試す

```bash
pip install -r requirements.txt
python -m playwright install chromium
WATCH_CONFIG="$(cat config.yaml)" python watch.py --dry-run
```

`--dry-run` は通知を送らずに取得と差分判定だけ行う。

## 実行間隔

**`schedule:` の cron は無料枠では額面通りに動かない。**
`*/10 * * * *`（10 分ごと）で 11 日間計測した実測値:

| 項目 | 実測 |
|---|---|
| 実行回数 | 47 回（10 分ごとなら 1,584 回） |
| 間隔の中央値 | **382 分（6.4 時間）** |
| 最小 / 最大 | 33 分 / 629 分 |

予約枠のような早い者勝ちの対象には間に合わない（実際に、空きを見つけてから
40 分で埋まった）。

GitHub が遅延させているのは `schedule` で、**API 経由の `workflow_dispatch`
には効かない**。そこで外部の cron サービスから API を叩いて起動する。

### 外部 cron から起動する

**1. 細粒度の個人アクセストークンを作る**

https://github.com/settings/personal-access-tokens/new

- Repository access: **Only select repositories** → このリポジトリだけ
- Permissions → Repository permissions → **Actions: Read and write**
- 他の権限は付けない

**2. cron サービスに登録する**（cron-job.org など。1 分間隔まで無料）

| 項目 | 値 |
|---|---|
| URL | `https://api.github.com/repos/<owner>/<repo>/actions/workflows/watch.yml/dispatches` |
| Method | `POST` |
| Header | `Authorization: Bearer <トークン>` |
| Header | `Accept: application/vnd.github+json` |
| Header | `X-GitHub-Api-Version: 2022-11-28` |
| Body | `{"ref":"main"}` |
| 間隔 | 10 分ごと |

成功すると **204 No Content** が返る（本文は空）。

**3. `schedule` は消さずに残す。** cron サービスが止まったときの保険になり、
そのときに下記の間隔監視が働く。

### 止まったことに気づく仕組み

外部 cron に任せると、**cron サービスの停止やトークンの期限切れで
「実行自体が起きない」**。通知が来ないだけなので、空きが無いのと区別がつかない。
実際にこの形で 10 日気づけなかったことがある。

そこで state に前回実行時刻を持ち、間隔が開いたら Discord で知らせる。

- 既定は **60 分**を超えたら通知（`WATCH_ALERT_GAP_MINUTES` で変更できる）
- 止まっている間ずっと鳴らないよう、**12 時間に 1 回**まで
- `schedule` の保険があるので、cron が死んでいても通知は届く

取得の失敗も同様に Discord へ送る（`notify_health`）。同じ故障で
鳴り続けないよう、エラーの指紋が変わったときだけ送り、復旧も知らせる。

**黙って 0 件を返す実装にしないこと。** 故障が「異常なし」と同じ見た目になる。

## 状態

前回の指紋は `state.json` に置く。Actions では `actions/cache` で
実行間を受け渡す。通知に失敗した場合は指紋を戻すので、次回あらためて
通知される（取りこぼさない）。

`__` で始まるキーは監視対象ではなく内部用（最終実行時刻・エラーの指紋）。

踏んだ罠:

- **`actions/cache`（まとめ版）の保存は後処理で走るため、ジョブが失敗すると
  保存されない。** 状態が前に進まず、失敗が延々と続く（28 回連続で起きた）。
  `actions/cache/restore` と `actions/cache/save` に分け、save は `if: always()`
- **導入ステップを `if: cache-hit == 'true'` で飛ばすと、一度不完全な
  キャッシュが保存された時点から永久に壊れる**（キーが固定なら自然復旧しない）。
  `playwright install` は冪等で速いので、キャッシュがあっても毎回走らせ、
  起動確認まで行う
- ブラウザの起動失敗を各 source の try の外で起こすと、例外が main まで
  抜けて**状態ファイルが一切書かれない**。受け止めて「全 source がエラー」にする

## ページ監視で「中身は同じなのに毎朝鳴る」とき

aromamore の各セラピストのページには **今日から 7 日分** の出勤表が載る。
窓が毎朝ひとつずれるので、本文をまるごとハッシュにすると、
中身が何も変わっていなくても全員分が毎朝「更新あり」になる。
「本日出勤」バッジも同じ理由で毎日出入りする。

そのため `fetch_static_html` は指紋を次の形で持つ。

```json
{"v": 2, "body": "<出勤表を除いた本文の md5>", "schedule": {"11/21": "歌舞伎町 満枠", ...}}
```

比べ方（`static_changed`）:

- `body` が違う → 通知する（コメントやクチコミの追加など）
- 出勤表は **前回と今回の両方にある日付だけ** で比べる。
  窓がずれて消えた日・現れた日は変化として扱わない
- 指紋が旧い形式なら、変化なしとして黙って作り直す
  （形式を変えた直後に全員分が一斉に鳴るのを防ぐ。取りこぼしは一度きり）

通知には「何が変わったか」を 1 行添える。
開いても違いが分からない通知は、鳴っていないのと同じくらい役に立たない。

取得の待ち時間は 30 秒、接続の不調は一度だけ取り直す。
15 秒では 15 件中 2 件が時間切れになり、
「監視が失敗しています」が無駄に鳴っていた。

## 実行が上限で殺されると、同じ通知が繰り返される

状態（前回の指紋）を **最後にまとめて** 書いていたため、
`timeout-minutes` で途中停止させられると状態が一切進まなかった。
実測では直近 30 回のうち 24 回が cancelled で、
`Run` は 880 秒（15 分の上限）まで走って殺されていた。
通知はコレクションごとに送られるので、
**通知だけ出て状態は巻き戻る → 10 分おきに同じ通知が届く**、という形になる。

対策:

- 指紋は **1 件ごとに** 書き出す。途中で殺されても進捗が消えない
- `WATCH_RUN_BUDGET_SECONDS`（既定 420 秒）を超えたら自分で止まる。
  殺されるより、止まって状態を残す方がよい
- 予算はコレクションで分け合う。先頭が使い切って
  予約枠の監視に一度も届かない、という形を作らない
- 予算の半分を超えたら、どこに時間を使ったかを `::warning::` 注釈に出す
  （ログ本体は認証が要るが、注釈は公開 API から読める）

エラーの指紋からは数字を伏せる。「時間切れで 13 件」「12 件」が
別の故障と見なされると、同じ不調で鳴り続けるため。

## 予約枠（grow-appt）は並列化できない

Actions から見ると 1 件あたり約 26 秒かかり、16 件を順に回すと
7 分を超えて予算に達していた（手元では 7.5 秒／件）。
待ち時間がほとんどなので同時に開けば速くなるはずだが、**できない**。

- 同じコンテキストを共有して同時 4 件 → 16 件中 8 件が時間切れ。
  このサイトは選択状態をサーバー側セッションで持つため、
  Cookie を共有したまま並べると互いの手順を壊し合う
- コンテキスト（Cookie）を分けて同時 3 件 → **16 件すべて時間切れ**。
  `goto` すら返らなくなる。サイト側が同時接続を捌けない

ただし **1 件ごとにコンテキストを作り直してもいけない**。
キャッシュが毎回空になり、1 件 26 秒だったものが 65 秒に落ちて、
16 件中 7 件しか回れなくなった。
使い回す本数を同時実行数に合わせ、順番に貸し出す。

したがって `GROW_CONCURRENCY = 1`。速くするのは諦めて、
**時間内に回りきらなかったぶんは次回の先頭から続ける**（`__cursor__`）。
毎回先頭から始めると、後ろのセラピストが永久に確認されない。

時間内に届かなかった対象は「故障」として通知しない。
巡回のたびに名前が変わるため、鳴らすと同じ不調で鳴り続ける。
取りこぼしは `::warning::` 注釈に出し、
**1 件も確認できなかったときだけ**故障として扱う。

### 1 件あたりの実測

| 場所 | 1 件 | 16 件 |
|---|---|---|
| 手元 | 7〜15 秒 | 2〜4 分 |
| Actions | **約 64 秒** | 約 17 分 |

Actions の回線からは桁違いに遅い。これが
「`Run` が 880 秒まで走って 15 分の上限で殺される」の正体だった。
効かなかった手（どれも 7/16 のまま変わらず）:

- コンテキスト（Cookie・キャッシュ）の使い回し
- 画像・フォント・動画を読まない（通信量を削る）

遅いのは帯域ではなく、このサイトの応答そのもの。
Actions の IP に対して速度を絞られている可能性が高い。
手元からは 7〜15 秒で返る同じページが、Actions からは 64 秒かかる。

いまは巡回で 1 回 7 件ずつ確認し、**約 23 分で全員を一周**している。
取りこぼしは出ないが、空き枠の検出は最大 23 分遅れる。
これ以上速くするには、**16 人を複数のジョブに分けて別々のランナーで走らせる**
（IP が分かれるので速度制限を避けられ、同時にも走る）必要がある。
状態キャッシュをジョブごとに分ける作りに変える必要があり、未着手。
